01 — Introduction

What FEILIAN is

FEILIAN is a candidate submitted to the Next-generation Commercial Cryptographic Algorithms programme (NGCC-CH) under the designation hash-10. It runs a 1024-bit chaining state with a 1024-bit message block; the compression function is a tweakable ARX permutation under a Davies–Meyer feed-forward. All three digest lengths reuse the same 1024-bit internal state — only the output is truncated — so one core implementation serves the whole family.

Design highlights

  • HAIFA-style iteration with a public tweak
  • Davies–Meyer feed-forward: h′ = v₀ ⊕ v₅ = E(h) ⊕ h
  • Permutation E: 20 rounds in 5 phases, two SubColumn layers per round
  • Strictly ARX — additions, rotations and XORs only; no message-word re-ordering, no linear expansion
  • Six rotation constants in total: 5, 48, 8 and 11, 40, 63

Public tweak tw = (ver, flag, t₀, t₁)

  • Version ver — 64-bit: 0x200 / 0x300 / 0x400 for 512 / 768 / 1024
  • Final-call flag flag — 64-bit, 0 or all-ones, distinguishing the last block of a message
  • Counter t — 128-bit message-bit count, split t₀‖t₁

Version, flag and counter are folded into every compression, so the same block processed at a different position in a different variant is a different computation. The counter is what binds the true message length under zero-only padding.

The design in one picture

Each of the five phases holds four rounds: one message-bearing round R⊕ followed by three message-free rounds R. Message halves are absorbed at rounds 1, 5, 9, 13 and 17, so the last injection is round 17.

03 — Third-party analysis

Independent reviews and their status

Three independent sources have analysed this submission. None of them establishes a full-round cryptanalytic break of the correctly encoded software hash. What follows is what each one found, and the current status of every finding against the material distributed here.

Mounir Idrassi — technical assessment

v1.0.2 · 27 September 2026 · 14 pp. · AM Crypto, Japan · CC BY 4.0

“Withhold a positive security assessment and integration approval for this submission… These are sufficient grounds to request a corrected submission and renewed review.”

Eight findings, R1–R8, spanning the RTL wrappers, the C sources, the mathematical argument and the shared test infrastructure. It states plainly that it does not establish a full-round break of the hash defined by the written compression algorithm, or of the normally operating C implementations.

The hardware conclusions are source-level: no RTL simulation was performed, so the assessment itself calls for end-to-end validation of any corrected implementation.

Markku-Juhani O. Saarinen — ngcc.dev

23 & 26 September 2026 · personal report · unaffiliated with NICCS

Reference C implementations return success with an all-zero digest when the padding allocation fails.

This is the earlier, source-level finding on which the assessment's R5 builds: the assessment extends the observation to the optimized SIMD implementations and credits the original report.

The site publishes follow-up RTL simulations and reference-C partial-byte checks. The assessment attributes those to that venue and does not rerun them; this page does the same, and cites them as reports rather than as reproduced results.

Mounir Idrassi — ePrint 2026/2236

submitted 27 September 2026 · approved 28 September · CC BY 4.0

“The component results establish no hash attack or bound on the hash's security margin.”

A complete classification of the whole-output linear structures of the 64-bit SubColumn. For FEILIAN's parameters the structure space is exactly the two-dimensional MSB family, with three nonzero members, and no nonzero member survives the second SubColumn boundary.

It is a component-level structural property — not a security ranking of any hash construction, and not a claim about FEILIAN as a whole.

What none of these analyses claim

None of the three establishes a full-round cryptanalytic break of the hash defined by the written compression algorithm, or of the correctly encoded software implementations. The assessment says so in as many words; the component paper says so in as many words.

The strongest concrete finding was the hardware length-binding defect (R1); the recommended remedy was to stop using the affected RTL implementations, and v1.0.1 corrects them (§04). Separately, all six supplied C implementations pass every entry of their KAT files — 24,582 comparisons — and the reproducibility of those vectors is what R8's test-infrastructure defects do not touch.

04 — Erratum

The designers' erratum: v1.0 → v1.0.1

On 8 October 2026 the designers released specification version 1.0.1 together with a two-page erratum that records every change made to the June 2026 text. The erratum is reproduced below in full. Its opening note is the single most important sentence in it, and it is quoted verbatim: “The design of hash function FEILIAN does not change. All details should refer to the reference code that illustrates FEILIAN correctly and fully.”

Design unchanged — typographies, not structure

No round, constant, counter rule or iteration count is altered by v1.0.1. Four typographical errors are corrected in the specification (Table 1 of the erratum). The implementations are refined towards the full-fledged version, not repaired: the erratum states plainly that “the software implementation (both reference and optimized codes) are correct”. Its own summary of the software changes is that they (1) handle exceptional execution situations properly, (2) handle non-full-byte strings properly, and (3) correct some inconsistency in program comments.

The distinction matters for reading §03: the compression function, the IV, the round constants and the counter conventions are what the third-party analyses examined, and none of them moves here.

2 · Corrections to the implementations

Table 2 of the erratum, grouped as the erratum groups it into software and hardware.

Software

IssueChange
Allocation failurepad_message() returns 0 if allocation fails; the internal hash function detects this and returns −1; CryptHash() propagates the error.
Non-full-byte stringAfter copying the input, pad_message() masks the unused low-order bits of the final byte when msg_bits % 8 != 0. Those bits are cleared before compression.
Length representabilityBefore converting the input length to size_t, CryptHash() checks whether it is representable. pad_message() computes the rounded-up byte and block counts by division and remainder, then checks num_blocks > SIZE_MAX / BLOCK_BYTES before computing the allocation size.
Non-compliant usageThe requested digest length is checked against the current version (512/768/1024) and an error is returned when it does not match.
Counter-word commentshash_bits[0] holds the high word; hash_bits[1] holds the low word.

Hardware

IssueChange
Current block length omitted in 1SC/4SC/8SCThe 1SC/4SC/8SC cores are revised so that the current block length is included in the compression input.
Block / final flag / cumulative length made transaction-consistentThe message block, the tweak (including the final flag and the cumulative bit count) and the initial chaining state are latched when a compression transaction is accepted, and preserved throughout compression.
Counter-word orderingAll RTL implementations use the same ordering: domain word 2 carries the upper 64 bits, domain word 3 the lower 64 bits.
Digest variantsAll four architectures support 512/768/1024 configurations.
Parameter propagationThe top-level DIGEST_BITS parameter is forwarded to the core, which derives the version value and the output-word count; digest selection and MMIO address bounds now follow the configured output length.
Intermediate state exposure and clearingThe 1SC/2SC/4SC cores restrict the digest output to completed hashes; the top-level MMIO read path is restricted the same way.
README typoFixed so the README states that the four RTL architectures support three instances, and that the architecture names indicate SubColumn parallelism.

3 · Further text changes made in response to the assessment [2]

Beyond the typos, the erratum lists four additions the designers made after reading the community assessment.

  • p. 18, §4.2 — more detailed NIST SP 800-22 test results are provided.
  • p. 19, §4.3.1 — the notations in the indifferentiability proof are unified to be fully consistent with FEILIAN, while sketching and adapting the HAIFA proof.
  • p. 37, §6.2 — a footnote is added to emphasise the necessity of an unambiguous encoding of context and counter.
  • pp. 37–38, §6.3 — a note is added clarifying that the XOF should be regarded as a variable-output-length hash function, leveraging the same FEILIAN-f compression function.

How this maps onto the findings of §03

The erratum is the designers' response to the assessment. Read against the R-numbers of §03, the corrections above fall out as follows.
